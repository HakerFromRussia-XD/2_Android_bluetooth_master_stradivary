# Постепенный рефакторинг UBI4 и V3

Дата исходной проверки: 2026-09-08. Базовый commit: `d21d6b5fe`.

## Согласованные границы

- Сохраняем Gradle-модули `app`, `shared`, `bluetooth`, `delegateadapter`.
- Рефакторим обе версии внутри UBI4: динамическую UBI4 и V3 с заданным приложением набором виджетов.
- Приоритет по решению пользователя: сначала перенос V3 (STANDARD_V3 и INDY3), затем динамическая UBI4. Между версиями после первого примера не переключаемся; обе переносим небольшими шагами.
- Для каждой версии постепенно создаём собственные `presentation`, `domain`, `data` внутри `app`.
- Существующие `BLEParser` и `BLEParserV3` остаются в `shared`; их реализации не объединяем и не перерабатываем.
- Текущая генерация виджетов внутри парсеров также сохраняется.
- На начальных этапах существующий `shared/commonMain` используется через Android-адаптеры без изменения его кода и контрактов.
- Не редактируем `iosApp`, `shared/src/iosMain`, `old_electronic_by_Misha`, `new_electronic_by_Rodeon`.
- XML, Compose и OpenGL сохраняют текущий способ отображения.
- Сохраняем протокол, порядок команд, существующее подключение, очередь, хранилища, имя базы и ключи настроек.
- Один запрос — один небольшой законченный шаг. После проверки фиксируем результат и следующий шаг.
- Новые и перерабатываемые экраны строим по MVVM с однонаправленным потоком состояния в стиле MVI. Правило действует отдельно для UBI4 и V3.
- По решению пользователя исправление `BindingGroupV3Test` отложено. Ошибка запуска тестов `shared` остаётся известным ограничением и не блокирует следующие согласованные шаги.

## Исходные цепочки

Обозначения путей ниже относительны корню репозитория. Android-классы находятся в
`app/src/main/java/com/bailout/stickk/ubi4`, общие классы — в
`shared/src/commonMain/kotlin/com/bailout/stickk/ubi4`.

| Участок | UBI4 | V3 |
| --- | --- | --- |
| Выбор версии | `ui/main/MainActivityUBI4.kt`, `initAllVariables()` устанавливает режим и профиль | Та же точка входа, включая профиль `INDY3` |
| Инициализация | `ble/BLEController.kt`, `smartInitWithCrc()`: сравнение CRC, загрузка описаний или восстановление кеша | `generatedHardcodeWidgets()` / `generatedHardcodeWidgetsINDY3()`, затем `initRequestsV3()` |
| Основные входящие данные | `BLEController.parseReceivedData()` → `BLEParser.parseReceivedData()` | `parseReceivedDataV3()` → `BLEParserV3.parseReceivedData()`; поток сенсоров обрабатывается отдельно |
| Состав виджетов | Описания устройства, при подходящем CRC — сохранённый кеш | Основной набор задан внутри `BLEParserV3`; значения поступают от устройства |
| Подготовка отображения | `UiState.listWidgets` → `DataFactory.prepareData(display)` → адаптеры UBI4 | Та же существующая инфраструктура списка, адаптеры V3 |
| Отправка изменений | Адаптеры и экран связаны с текущими командами и очередью Activity | Например, `SliderDelegateAdapterV3` кодирует действие, обновляет состояние/профиль и вызывает `main.bleCommandWithQueue()` |

Эта карта фиксирует текущие точки взаимодействия, а не предписывает перенос парсеров.
Для первого изменяемого параметра отдельно прослеживаем точный набор команд,
подтверждения, повторные запросы, сохранение и восстановление значения.

## Целевые границы внутри app

```text
ubi4/
├── navigation/
├── di/
└── versions/
    ├── ubiv4/
    │   ├── presentation/
    │   ├── domain/
    │   └── data/
    └── v3/
        ├── presentation/
        ├── domain/
        └── data/
```

Это направление размещения. Пустые пакеты заранее не создаём, существующие файлы
массово не переносим. Код группируется по конкретным сценариям по мере миграции.

- Направление зависимостей: `presentation → domain ← data`.
- Новые domain-контракты не содержат Android Context, View, Compose, Room Entity и деталей BLE-пакетов.
- Data-адаптер соответствующей версии связывает контракт с существующим parser/state/storage/transport.
- UI и ViewModel не используют парсер или `MainActivityUBI4.main` напрямую.
- Общие KMM-алгоритмы не копируются в Android. Новое состояние экрана не становится вторым независимым хранилищем состояния устройства.
- Начальное внедрение зависимостей: конструкторы и небольшие фабрики. Hilt/Koin и обновление библиотек в этот план не входят.
- ViewModel создаётся через Android lifecycle; Activity и View не удерживаются долгоживущими объектами.
- Самостоятельный UseCase появляется для содержательного сценария. Простое чтение может идти через интерфейс репозитория.
- Отдельные реализации версий не создают два одновременных подключения или дублирующие базы.
- В одном Gradle-модуле границы поддерживаем проверкой импортов и ревью; сами папки их не обеспечивают.

### UseCase и направление зависимостей

В `domain` размещаем UseCase (сценарии работы с настройками), интерфейсы
репозиториев и необходимые предметные модели. Внутри версии они группируются
по области: например, `domain/settings/usecase/`. UseCase работают с интерфейсом
`V3DeviceSettingsRepository`; реализация `V3DeviceSettingsRepositoryImpl`
находится в `data/settings/`. Суффикс `Impl` означает реализацию интерфейса,
название не указывает на временность или возраст кода.

Зависимости исходного кода: `presentation → domain ← data`.
Domain не импортирует presentation/data, Android, BLE-пакеты или Room.
ViewModel зависит от UseCase и domain-моделей; UseCase — от domain-контрактов.
UseCase содержит правила и координацию содержательного сценария, а не создаётся
автоматически для каждого виджета или простого метода чтения.
Обработка жестов UI, анимации и формирование UiState остаются в presentation.

Путь действия во время выполнения: UI → ViewModel → UseCase → интерфейс
репозитория → его data-реализация → существующее хранилище/очередь.
Обновления данных идут обратно через контракт репозитория к ViewModel и UiState.
Это поток вызовов и значений, а не обратная зависимость domain от data.
Создание конкретных реализаций и соединение зависимостей выполняет точка сборки;
сейчас это подключение в `BaseWidgetsFragment`, позднее небольшая фабрика.

После шагов 4 и 6 `SliderItemV3` с `P_KEY_SPEED_SETTINGS` и `P_KEY_FORCE_SETTINGS` использует ViewModel:
запись проходит через `SetSliderValueUseCaseV3`, наблюдение — через domain-контракт.
Остальные параметры и общие хранилища пока обслуживает прежний код,
поэтому весь проект ещё не соответствует целевой архитектуре.

## MVVM и управление состоянием

- MVVM определяет ответственность View, ViewModel и model/data-слоя.
- MVI используем как организацию потока: пользовательское `Action` → обработчик ViewModel → новое неизменяемое `UiState` → отображение. Данные репозитория также обновляют состояние.
- ViewModel отдаёт только `StateFlow<UiState>`; изменяемый поток остаётся приватным. UI не меняет состояние напрямую.
- Изменение состояния и выполнение побочных действий разделены: reducer, если он нужен, остаётся чистой функцией; BLE/БД вызываются через domain-контракт вне reducer и вне `MutableStateFlow.update`.
- Обновление UI из репозитория, повторная подписка и программное изменение SeekBar не отправляют команды устройству.
- MVI не заменяет хранение данных. `StateFlow` содержит состояние экрана в памяти; существующие Room/настройки/состояние устройства сохраняют свои обязанности. `SavedStateHandle` используем только при реальной необходимости восстановить локальное UI-состояние после пересоздания процесса.
- Обработка действий и отложенных отправок должна иметь явный порядок. Повторный вход на экран не воспроизводит уже отправленные действия.
- Одноразовые эффекты вводим только при необходимости и с понятными правилами доставки. Значимый результат операции или ошибка не должны теряться при отсутствии подписчика.
- Отдельная MVI-библиотека и универсальные базовые Store/ViewModel для первого сценария не нужны.
- ViewModel относится к экрану или самостоятельному блоку настроек. Один параметр не получает собственные ViewModel и репозиторий автоматически. После первого примера переносим небольшие группы с одинаковым поведением.

Основа для state holder и `StateFlow`: [Android UI state production](https://developer.android.com/topic/architecture/ui-layer/state-production).
Правила обработки результатов событий: [Android UI events](https://developer.android.com/topic/architecture/ui-layer/events).

## Названия и ответственность новых классов

Для виджетов используем существующие названия из `WidgetsItem.kt` и адаптеров.
Они являются основной терминологией миграции; название одного параметра не
становится новым названием типа виджета. Существующие суффиксы `V3` сохраняем.

| Виджет | UBI4: существующие item / адаптер | V3: существующие item / адаптер |
| --- | --- | --- |
| Slider | `SliderItem` / `SliderDelegateAdapter` | `SliderItemV3` / `SliderDelegateAdapterV3` |
| ToggleSlider | `ToggleSliderItem` / `ToggleSliderDelegateAdapter` | `ToggleSliderItemV3` / `ToggleSliderDelegateAdapterV3` |
| Switch | `SwitchItem` / `SwitcherDelegateAdapter` | `SwitchItemV3` / `SwitcherDelegateAdapterV3` |
| Spinner | `SpinnerItem` / `SpinnerDelegateAdapter` | `SpinnerItemV3` / `SpinnerDelegateAdapterV3` |
| Plot | `PlotItem` / `PlotDelegateAdapter` | `PlotItemV3` / `PlotDelegateAdapterV3` |
| Gestures | `GesturesItem` / `GesturesDelegateAdapter` | `GesturesItemV3` / `GesturesDelegateAdapterV3` |
| Кнопки | `OneButtonItem` / `OneButtonDelegateAdapter` | `ButtonsItemV3` / `ButtonsDelegateAdapterV3` |
| TextInput | — | `TextInputItemV3` / `TextInputDelegateAdapterV3` |

Это карта основных типов, а не перечень всех специальных адаптеров.
Точный первый участок: `SliderDelegateAdapterV3` → `SliderItemV3` →
`P_KEY_SPEED_SETTINGS` («Настройка скорости»).
Для новых моделей состояния и действий виджетов сохраняем корни `Slider`,
`ToggleSlider`, `Spinner` и другие существующие названия. Конкретный параметр
различается своим ключом; отдельный набор Speed-классов и действий не закрепляем.
Это не требует переноса parser/widget-структур в domain.

Названия ниже описывают классы уровня экрана и данных, а не названия
виджетов. Для этих классов используем префиксы `V3` и `Ubi4`;
`INDY3` остаётся профилем V3. Существующие классы не переименовываем.
Контракт и data-реализация V3 добавлены на шаге 3; классы экрана и UseCase
подключены на шаге 4 для скорости, на шаге 6 добавлена сила.
Оба параметра используют одну ViewModel; `V3AdvancedSettingsUiState.sliders`
содержит состояния по существующим ключам, отложенные записи также разделены по ключам.

| Название | Ответственность |
| --- | --- |
| `V3AdvancedSettingsViewModel` | Логика перенесённой части дополнительных настроек V3, отображаемых в существующем `AdvancedFragment` (`display = 2`) |
| `V3AdvancedSettingsUiState` | Неизменяемое состояние перенесённой части этого экрана; расширяется по мере миграции |
| `V3AdvancedSettingsAction` | Действия пользователя на этом экране, с сохранением терминологии типов виджетов и идентификацией параметра по ключу |
| `V3AdvancedSettingsViewModelFactory` | Создание этой ViewModel с зависимостями через Android lifecycle |
| `V3DeviceSettingsRepository` | Domain-контракт чтения и изменения настроек устройства V3; первая реализуемая часть — скорость |
| `V3DeviceSettingsRepositoryImpl` | Data-реализация контракта поверх существующих механизмов V3: состояния, codec, сохранения профиля и очереди отправки |

Расположение: `versions/v3/presentation/advancedsettings/` для классов экрана,
`versions/v3/domain/settings/` для контракта,
`versions/v3/data/settings/` для его реализации.
Репозиторий именуется по данным устройства и может обслуживать несколько экранов.
Он не становится общей точкой для прошивки, подключения и всех функций V3.
Добавляем только операции, нужные переносимому сценарию, без универсального API заранее.

Для соответствующего экрана динамической UBI4 используем
`Ubi4AdvancedSettingsViewModel`, `Ubi4AdvancedSettingsUiState`,
`Ubi4AdvancedSettingsAction`, `Ubi4AdvancedSettingsViewModelFactory`,
`Ubi4DeviceSettingsRepository` и `Ubi4DeviceSettingsRepositoryImpl`
в аналогичных пакетах `versions/ubiv4/`.
Состав состояния UBI4 учитывает описания динамических виджетов; одинаковый принцип
именования не требует одинаковых моделей и реализации двух версий.

Скорость — первый сценарий внутри этих границ, а не отдельный экран:
`SpeedSettingsViewModel` и отдельный репозиторий на каждый виджет не планируются.
