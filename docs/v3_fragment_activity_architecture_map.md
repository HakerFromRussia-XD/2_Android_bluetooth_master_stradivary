# C4 — оставшиеся обязанности Fragment и Activity для V3

Актуальная транспортная структура после упрощения C4.20–C4.23: один
V3CommandTransport ставит пакеты в прежнюю очередь; BleCommandWriter выполняет
синхронную запись UBI4 и writeAsync для V3 с переданным lifecycleScope/IO.
V3CommandExecutor и V3TransportDependencies удалены; сборка объединена в
BleDependencies. Исторические описания ниже отражают промежуточные шаги.
Из тестов удалена копия исходного launch-блока, пять сценариев проверяют writer.
Проверено: 758 app-тестов, debug/release; Samsung + 00001, синхронизация и
четыре экрана без новых падений, содержимое XML совпало. Запись параметров,
движение, прошивка и физический UBI4 не проверялись. Рабочий код: −12 строк,
тестовый: −10 строк; удалены два рабочих файла (относительно начала упрощения).

Дата: 2026-09-18. Область — V3 (STANDARD_V3 и INDY3). Общие файлы
сохраняют UBI4-пути. SprTrainingFragment и MotionTrainingFragment относятся
к UBI4 по уточнению пользователя: обучение не переносим и не удаляем.

Актуальное ограничение пользователя: AdvancedFragment и его Slider binder, lifecycle,
маршруты и сборка зависимостей исключены из дальнейшего рефакторинга. C4.11 отменён.
Исторические предложения переноса Advanced ниже более не действуют.

## C4.2 — сборка зависимостей «Датчиков»

В V3SensorsViewModelFactory добавлен конструктор для существующих callbacks:
передача пакета в очередь, показ синхронизации, обновление виджетов. Он создаёт
прежние репозитории параметров, графика, команд и сессии, а также источник состава
виджетов. Конструктор с domain-контрактами сохранён для поведенческих тестов.

Из Base удалены createV3SensorsPlotRepository/createV3SensorsCommandsRepository
и их импорты: единственный потребитель был SensorsFragment. Общий
createV3DeviceSettingsRepository после C4.4 нужен только Slider binder для Advanced.
SensorsFragment больше не создаёт репозитории или DataFactoryV3SensorsWidgetsSource.

Сами callbacks дословно сохраняют прежние обращения к MainActivityUBI4.main,
SERIALPORTCHAR_UUID и WRITE. Они не захватывают Fragment/Activity; обращение к
текущей Activity по-прежнему происходит при вызове. Создание и lifecycle ViewModel,
все UseCase, data-реализации, UiState/Action и render остаются прежними.
Работа UBI4 в SensorsFragment и общая композиция адаптеров Base не изменены.
Новых production-классов нет; в трёх production-файлах +24/−17 строк.

Проверки: 735 app-тестов, включая 17 архитектурных, без ошибок и пропусков;
debug/release собраны. Проверка границ запрещает возвращать создание репозиториев
в SensorsFragment и зависимости data.sensors в Base. Лог: /tmp/v3-sensors-di-build.log.
Итоговый release установлен на Samsung R8YX900N0JK с сохранением данных.
Подключение к реальному 00001 восстановилось; проверен переход «Датчики» →
«Спецнастройки» → «Датчики». У 29 элементов экрана совпали текст, координаты и
доступность до/после установки и повторного входа; пороги 171/109, слайдеры 41/62
сохранены. Crash-журнал не изменился. Команды движения, изменение параметров и
принудительное обновление виджетов на устройстве не запускались.
Физические UBI4/INDY3 не проверялись; сохранность их правил подтверждается
неизменёнными ветками/реализациями и существующими поведенческими тестами.

## C4.4 — сборка зависимостей «Служебных настроек»

V3ServiceViewModelFactory.create собирает репозитории параметров, роли, данных
устройства, калибровки и сессии, а также прежний источник виджетов. Один экземпляр
репозитория параметров используется Slider, Spinner и репозиторием роли. Для роли
сохранён context.getSharedPreferences(APP_PREFERENCES, MODE_PRIVATE); фабрика
не хранит Context. Конструктор с domain-контрактами остаётся для тестов.

ServiceFragment передаёт прежние callbacks чтения серийного номера, имени,
имени из Intent, немедленного обновления имени и очереди. Они обращаются к
MainActivityUBI4.main при вызове, не захватывая Fragment или конкретную Activity.
Callback завершения записи передаётся репозиторию данных устройства без замены;
для параметров и калибровки фабрика передаёт прежний пустой callback.

Из Fragment удалены создание репозиториев/источника виджетов и связанные импорты.

включая UBI4, lifecycle и render, а также прежней сборки UseCase/ViewModel.
Сами data/domain/presentation-реализации, UI и протокол не менялись.
Новых production-классов нет. Общий метод Base сохранён для Advanced.

возвращать V3 data/Repository/UseCase, создание источника виджетов и preferences в UI.

## C4.6 — адаптеры «Датчиков» принадлежат экрану

SensorsFragment создаёт собственные PlotDelegateAdapterV3, SensorsButtonsDelegateAdapterV3,
SliderDelegateAdapterV3 и CompositeDelegateAdapter для V3. Эти три типа покрывают
весь состав V3SensorsWidgetMapper для STANDARD_V3/INDY3. Относительный порядок
адаптеров сохранён: Plot, Buttons, Slider; порядок виджетов по-прежнему задаёт UiState.
Ветка UBI4 получает прежний super.adapterWidgets и использует прежний bindUbi4Widgets.

Экран непосредственно отображает state.plot/buttons/sliders и передаёт действия
в свою ViewModel. Промежуточные render/action-методы Plot и SensorsButtons из Base
удалены вместе с их полями и зависимостями от состояния «Датчиков». Общий Slider
и его методы пока нужны «Спецнастройкам», Service и Advanced.

Общий набор Base сохранён полностью и в прежнем порядке. DataFactory всё ещё
поддерживает PlotItemV3/ButtonsItemV3, поэтому поддержка этих типов в общем наборе
не удалялась: там остались адаптеры с прежними пустыми обработчиками для экранов,
не имеющих V3SensorsViewModel. Рабочие V3-адаптеры «Датчиков» теперь создаёт только
SensorsFragment. При выборе V3 общий набор Base для SensorsFragment не создаётся.

Все три экранных адаптера регистрируют очистку через registerDelegateCleanup;
releaseDelegateResources, порядок onDestroyView и отключение RecyclerView сохранены.
Повторное использование view holders, регистрация очистки и обработка действий
внутри адаптеров не менялись. Логика ViewModel, domain/data и состав виджетов прежние.
Сравнение с копией до шага подтвердило неизменность UBI4-binding, teardown,
V3-binding и общего набора Base после подстановки двух прежних адаптеров.
Новых production-классов нет.

### Фактическая цепочка и ограничения

- Четыре фабрики передают callback репозиториям; отправка идёт через текущую
  MainActivityUBI4.main с SERIALPORTCHAR_UUID/WRITE. Service сохраняет исходный
  onSent, остальные сценарии передают пустое завершение. Emulator hook выполняется
  в Activity до постановки в очередь; новый адаптер должен проходить через него.
- Activity владеет BlockingQueueUbi4, remainingTasks, worker и writeLock.
  startQueue вызывается при создании Activity. Очередь извлекает задачи по порядку,
  разрешая следующую по allowNext от парсеров либо автоматически через 300 мс.
  Оба парсера пользуются той же очередью: переносить/подменять её только для V3 нельзя.
- У V3 Runnable запускает lifecycleScope.launch(Dispatchers.IO), у UBI4 writeData
  вызывается синхронно. Worker уменьшает remainingTasks после task.run: для V3
  это НЕ гарантирует завершения BLE-записи. Порядок извлечения из очереди не следует
  выдавать за доказательство порядка выполнения IO-coroutines.
- writeData вызывает BLEController.bleCommand и ждёт canSendFlag через wait.
  При успешном GATT write сервис сообщает WRITE; BLEController выставляет флаг
  и notifyAll текущей Activity. Парсерный allowNext и GATT write — разные события.
- onSent вызывается после возврата writeData. При dispatched=false writeData
  возвращается без отправки, но прежний код всё равно вызывает callback.
  Это не receipt/ACK протеза и не новый контракт успешной записи. При исключении
  до возврата callback не вызывается. Эти особенности не исправлять попутно.
- onStop worker не останавливает; onDestroy выключает флаг worker, прерывает поток,
  вызывает cleanup BLEController и очищает mainRef, если это та же Activity.
  Отправки V3 принадлежат lifecycleScope, но блокирующее wait само по себе не
  гарантирует кооперативную отмену coroutine. При disconnect контроллер закрывает
  GATT/планирует reconnect; единой гарантии очистки ожидающих задач и завершений
  в просмотренной цепочке нет. Не добавлять её в рамках простого переноса.
- DFU ожидает remainingTasks и имеет отдельные прямые пути записи. Их семантику,
  задержки, счётчик, locks и передачу команд нельзя менять ради четырёх экранов.

## C4.21 — выполнение задачи V3 после извлечения из очереди

V3CommandExecutor в data/transport принимает scope, функцию writeData и dispatcher
(IO по умолчанию). Он запускает прежнюю последовательность writeData → onSent
в переданном scope. V3TransportDependencies собирает его для конкретной Activity;
Activity лениво передаёт собственный lifecycleScope и ::writeData. Экземпляр
не является singleton и не переживает владельца через глобальный binding.
В getBleCommandWithQueue V3-ветка вызывает execute; прежний launch-блок удалён.

и извлечённого исполнителя: асинхронный запуск/аргументы/порядок callback,
отмена до запуска, отмена во время синхронной записи, исключения записи и callback.
Сохраняется отсутствие дополнительной проверки отмены между writeData и callback.
Исключения обрабатываются исходным scope, повторов и собственной очереди нет.

Это перенос запуска V3-записи и завершения, а не всей BLE-инфраструктуры.
Общий writeData, writeLock/canSendFlag, worker, remainingTasks, onDestroy и DFU
остаются в Activity без изменений. UBI4 выполняется синхронно как прежде.
Проверка полного текста Activity относительно копии до шага подтверждает,
что изменились только импорт, binding и V3 launch-блок. Advanced и его binding,
UI, парсеры, KMM и iOS не редактировались.

## C4.22 — граница общей записи и уведомлений

Проверены все ссылки writeLock/canSendFlag в app/shared, отправка BLEController,
callback BluetoothLeService, инициализация/уничтожение Activity и прямые DFU-пути.

| Участок | Текущее поведение, которое нужно сохранить |
| --- | --- |
| Activity.setStaticVariables | Под writeLock устанавливает false и вызывает notifyAll; это не завершение записи. |
| Activity.writeData | Под тем же монитором ставит false, вызывает bleCommand; при отказе ставит true и возвращает, иначе ждёт в while. |
| BLEController WRITE callback | Сначала завершает pendingFirmwareControlWrite, затем получает mainOrNull; при его отсутствии выходит. Под монитором текущей Activity ставит true и уведомляет всех. |
| BluetoothLeService | Отправляет WRITE callback при GATT_SUCCESS; callback не содержит идентификатор ожидающей команды. |
| V3/UBI4 | Используют один writeData; V3 запускает его через lifecycleScope/IO, UBI4 — в worker. |
| DFU | Старый переход использует очередь; прямые control-записи имеют собственный deferred, но получают тот же WRITE callback. Reset с ожидаемым disconnect и writeWithoutResponse обходят очередь. |
| onDestroy | Прерывает worker и очищает BLEController; отдельного завершения writeLock нет. |

canSendFlag хранится в общем FlagState, а монитор принадлежит Activity. Перенос
флага в новый экземпляр изменил бы поведение при смене Activity. Callback сейчас
находит текущую mainOrNull, а не Activity, начавшую отправку; это также сохраняем.
READ/NOTIFY проходят через тот же bleCommand, поэтому нельзя сузить принимаемые
аргументы до WRITE только потому, что четыре V3-фабрики отправляют WRITE.
Парсерный allowNext очереди и GATT WRITE — разные события; объединять их нельзя.

Решение для C4.23: один BleCommandWriter в общей Android-папке ubi4/ble, а не
V3-копия writeData. Он получает функцию BLE-dispatch и владеет одним монитором;
write/reset/onWriteCompleted переносят существующие три synchronized-блока.
Существующий FlagState.canSendFlag и сообщения логов сохраняются. DI собирает
writer на Activity; Activity делегирует запись/сброс/уведомление. BLEController
по-прежнему завершает DFU deferred до mainOrNull и вызывает уведомление через
текущую Activity, но перестаёт напрямую изменять её монитор и флаг. Публичный
writeLock удаляется после проверки всех ссылок. Один и тот же writer используется
обеими ветками; UBI4-правила, worker, очередь, парсеры и DFU-алгоритмы не переносятся.

Перенос выполнить одним связанным изменением, без временного второго монитора.
Перед подключением проверить: отказ dispatch без ожидания; успешную запись с
ожиданием сигнала; сигнал во время dispatch; пробуждение без true; reset; исключение
и прерывание ожидания; прежний порядок V3/UBI4 и DFU callback. Не вводить таймаут,
повтор, дополнительную отмену, привязку callback к пакету или новый ACK-контракт.
После подключения — app-тесты/debug/release и навигация/синхронизация Samsung 00001.
Физическая навигация V3 не заменяет проверки прошивки и аппаратного UBI4.

аппаратная проверка повторно не запускались. C4.23 — реализация этого решения.

калибровки, запись параметров и прошивка не запускались. Физические UBI4/INDY3
не проверялись; общие участки проверены тестами writer и сравнением кода.

## C4.24 — очередь, worker и счётчик вынесены вместе

Один BleCommandQueue владеет прежним BlockingQueueUbi4, AtomicInteger и worker.
Activity создаёт его на свой lifecycle без новой фабрики/интерфейса, делегирует
start/stop/enqueue и чтение pendingCount. Исходный startQueue и поля удалены.
Тело worker сравнено с копией до шага и совпало дословно (кроме имени метода).
Сохранены put → increment, decrement после Runnable.run, отсутствие decrement
при ошибке/прерывании, проверки флага/interrupt и имя потока. stop не очищает
очередь/счётчик и не добавляет join. Это перенос, не исправление прежних гонок.

Парсеры получают тот же объект очереди через getQueueUBI4; shared и allowNext
не менялись. DFU читает тот же AtomicInteger через pendingCount; ожидания, таймауты
и команды не изменены. V3/UBI4 выбор и выполнение Runnable сохранены в Activity.
UI, Advanced, BLEController, парсеры и KMM/iOS не редактировались.

Пять тестов до подключения проверили передачу packet/task по ссылке и порядок
put/increment, отказ put, порядок выполнения и повторный start, уменьшение
счётчика после возврата, продолжение после ошибки, остановку во время get и
прерывание выполняющейся задачи без очистки очереди/счётчика.
Далее C4.25: сверить оставшиеся V3-обязанности Activity (синхронизация/навигация)
с картой C4; не выносить естественные Android lifecycle/UI обязанности ради числа строк.

Проверки C4.24: 763 app-теста без ошибок/пропусков, debug/release собраны.
Release установлен на Samsung R8YX900N0JK с реальным 00001. Синхронизация
завершилась, переходы по четырём экранам выполнены. XML содержимого до/после
совпал, crash-buffer не изменился; служебная вкладка снова скрыта. Запись
параметров, движение, калибровка, прошивка и физический UBI4/INDY3 не проверялись.

## C4.25 — остаток синхронизации и навигации

Прослежены Activity → SyncProgressDialog и BottomNavigationController, вызовы
observeSyncProgress из Sensors DI/Base, события BLEController/парсера V3.

- Activity запускает первоначальный loader до создания BottomNavigationController;
  setChromeVisible(false) безопасен за счёт короткого замыкания условия. Этот порядок
  и немедленный show сохраняются, чтобы не вернуть мигание/обращение к lateinit.
- SyncProgressDialog сам подписывается на четыре общих потока UiState и содержит
  решения о показе/закрытии и восстановлении панелей. Это оставшаяся смешанная
  ответственность UI/глобального состояния; C4 ещё нельзя считать завершённым.
- startup имеет приоритет над fullInit; завершение current>=total закрывает диалог
  только после startup-ветки. При total=0 fullInit остаётся в ожидании. В рамках
  одного показа процент не уменьшается (maxOf текущего и нового), show сбрасывает его.
- widgetsLoadingFlow — отдельное событие закрытия, даже если флаги ещё true.
  Не заменять merge на combine без сохранения этого поведения. Новый прогресс
  или флаг может снова открыть диалог. Повторный observe отменяет старый watchJob,
  а STARTED-подписка восстанавливается после background с текущими значениями.
- syncShownOnce ограничивает ensureSyncDialogShown, но не прямой observeSyncProgress;
  ручное обновление в Sensors использует прямой вызов. Не объединять эти методы
  механически. Маршрут Advanced и общий binder остаются исключёнными.
- FragmentManager, back stack, hide/add/replace, анимации, IME и видимость панелей
  остаются UI-обязанностями. Новый Navigator/Host ради уменьшения Activity не нужен.
- computeVisibleDisplays пока обращается к DataFactory; это известная граница D2.
  BottomNavigationVisibilityPolicy уже отделяет выбор доступной вкладки. Её нельзя
  заменять захардкоженным V3-набором, пока состав зависит от существующего источника.
- BLEController/парсеры остаются источниками протокольной синхронизации; менять
  их генерацию запросов, критерии готовности и UBI4-инициализацию в этом шаге нельзя.

Следующий связанный шаг C4.26: состояние отображения синхронизации V3 через
ViewModel/UiState и UseCase/Repository для прежних событий. Диалог отображает
состояние; Activity связывает lifecycle и немедленный startup-показ. Путь UBI4
и его подписки сохраняются. Без дополнительного Controller/Host/StateHolder.
Сначала закрепить перечисленные переходы, повторное подключение наблюдения,
возврат из background и событие ready при ещё активных флагах, затем подключить
V3 и удалить его прежнюю обработку из UI. Один перенос всего сценария, не серия
пустых обёрток. Внешний UI, панели, анимации и парсеры сохраняются.

C4.25 завершён как сверка по плану: production-код не менялся, повторная сборка
и аппаратные тесты не запускались. Изменены только карта, план и статус ревизии.

## C4.26 — состояние отображения синхронизации V3

V3SyncRepositoryImpl читает прежние четыре потока UiState, сохраняя ready
отдельным событием и снимая startup/fullInit в момент исходного события.
ObserveSyncUseCaseV3 связывает domain-контракт с V3SyncViewModel. ViewModel
преобразует события в UiState: startup приоритетен, неизвестный total держит
загрузку, процент не уменьшается до reset/нового показа, ready закрывает независимо
от флагов, следующий прогресс может открыть снова. ViewCreated сбрасывает состояние
для нового экземпляра Activity; STOP отменяет источник, сохраняя видимое состояние.

Activity сохраняет немедленный startup show и прежнюю установку startup-флага.
Для V3 она подписывает renderer в STARTED, для UBI4 вызывает прежний обработчик.
Один lifecycle-наблюдатель состояния живёт в Activity; повторный observeSyncProgress
заменяет только подписку ViewModel на источник, исключая конкурирующие finally.
SyncProgressDialog.renderV3 не читает глобальные потоки, а применяет состояние.
chromeVisible=null означает отсутствие запроса менять панели; renderer сохраняет
прежний chromeHidden и меняет панели только при переходе. Это важно для навигации.

Старый observeSyncProgress диалога сохранён дословно для UBI4; V3 его больше
не вызывает. Общий код нельзя удалить до отдельного рефакторинга UBI4, который
исключён пользователем. XML/анимации, парсеры, протокольная инициализация,
Advanced и KMM/iOS не редактировались. Шесть production-файлов — контракт/события,
UseCase, data, ViewModel, UiState/Action и DI; дополнительных Host/Controller нет.

До UI-подключения прошли семь тестов: startup/fullInit, неизвестный total и
границы процента, монотонность/reset, ready и повторное открытие, warm ready без
изменения панелей, STOP/repeated attach, новая Activity/очистка VM и повторное
чтение текущих данных источника. Затем выполнены все app-тесты и сборки.
C4 остаётся открытым до итоговой сверки оставшихся обязанностей Activity/Base;
инициация протокола в BLEController и состав DataFactory не объявляются перенесёнными.

Проверки C4.26 завершены: 770 app-тестов без ошибок/пропусков, debug/release
собраны. На Samsung R8YX900N0JK с реальным 00001 приложение после установки
дошло до рабочего экрана. Четыре экрана совпали с XML до установки; служебная
вкладка снова скрыта. Проверены HOME → недавние приложения → карточка Моторика старт.
Первый кадр возврата содержал нулевые пороги/заблокированные контролы; повторный
снимок после восстановления данных полностью совпал с исходным. Причина/время
этого промежуточного состояния не сравнивались со старой сборкой. Crash-buffer
не изменился. Движение, запись параметров, прошивка, физические INDY3/UBI4
и возврат из фона во время незавершённой аппаратной синхронизации не проверялись.


## C4.27 — итоговая сверка Activity/Base (2026-09-21)

Проверены текущие тела методов Activity/Base, четыре экранных выбора адаптеров,
маршрут обновления Sensors и Android-потребители DFU. Это проверка границ по коду,
а не новое подтверждение поведения на устройстве.

| Ответственность | Решение / незавершённая работа |
| --- | --- |
| FragmentManager, back stack, панели, IME, анимации, Dialog | Оставить в Android UI; отдельный Navigator/Host ради сокращения строк не нужен. |
| Отображение синхронизации V3 | Уже ViewModel/UiState; Activity связывает lifecycle и немедленный startup-показ. Инициация протокола этим не перенесена. |
| initAllVariables/setStaticVariables, reconnect | Смешаны Intent/lifecycle и глобальная сессия/регистрация BLE. D2: отделить V3-данные, сохраняя порядок регистрации и подключения; парсеры не менять. |
| observeBattery, currentSerial, applyDeviceNameImmediately | Шапка ещё читает глобальные данные и меняет имя сессии. D2: данные через V3-контракты/состояние; цвета и Android View остаются UI. |
| TelemetryCoordinator, enqueueAppCloseUploadIfNeeded | Сборка и правила запуска ещё в Activity. D2: сохранить connection/STOP/DESTROY-триггеры, защиту повторного enqueue и отмену в onResume. |
| computeVisibleDisplays, updateFlow | Пока зависят от DataFactory; D2 вместе с V3-составом виджетов. Не заменять список вкладок константой. |
| preferences, WidgetRepoProvider | Общие API имеют старых потребителей; D2 переносит V3-потребление, не удаляет API UBI4. |
| firmwareJumpToBootloader и dfu* | C5: самостоятельный сценарий; Android shared-транспорты используют BleCommandExecutor через BleEnvironment. Queue drain, deferred и reset/disconnect различаются — не объединять механически. |
| Base: адаптеры и Slider binder | Четыре основных экрана выбирают собственные V3-адаптеры; super остаётся UBI4. Непустой v3SliderParameterKeys в Base-пути задаёт Advanced, исключённый пользователем. |
| Base: refreshWidgetsList | Sensors V3 отправляет RefreshRequested во ViewModel; UBI4 вызывает прежний метод. Общую fallback-ветку не удалять ради сокращения Base. |
| Base: lifecycle, диалоги, имена | Cleanup/rebind остаются UI; SprGesture V3 пропускает старое чтение имён. Другие наследники ещё вызывают базовое чтение preferences при onResume — это остаток D2, не полностью очищенный Base. |

C4.27 завершён без правок production-кода и тестов. C4 целиком не закрыт:
оставшиеся зависимости явно закреплены в D2/C5. Порядок C5 → D → E сохраняется;
после D2 нужна повторная сверка C4. Следующий небольшой шаг — C5.1, карта
редактора V3 до переноса его внутренней логики. Общий рендер и UBI4 сохраняются.

Новые сборки и аппаратные проверки не запускались: изменена только документация.
Результаты 770 тестов и Samsung выше относятся к C4.26.
