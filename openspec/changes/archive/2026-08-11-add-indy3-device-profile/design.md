## Context

См. `proposal.md` для мотивации и обе delta specs для проверяемого поведения.

Android сейчас решает связанные задачи в нескольких местах: `ScanActivity.checkOurLEName()` фильтрует найденные устройства булевым результатом, `getProtocolType()` отдельно определяет тип, `StartActivity` ещё раз определяет V3-режим, а `BLEController` всегда выбирает стандартные V3-виджеты и init-запросы. Общее состояние виджетов хранится в `UiState.listWidgets`.

iOS сохраняет выбранное BLE-имя и включает V3 через `UiInterfaceModeBridgeV3`, но список его V3-маркеров не содержит INDY3. После подключения iOS actual `BleManagerKmm` всегда вызывает стандартные `generatedHardcodeWidgets()` и `buildV3InitRequests()`. `MainTabBarController` формирует платформенные вкладки независимо от фактической доступности widgets по `display`.

`MainActivityUBI4.computeVisibleDisplays()` уже вычисляет непустые `display` в диапазоне `0..4`, но `BottomNavigationController.applyVisibility()` применяет этот результат только к `page_3`. Секретный пункт дополнительно управляется сохранённым флагом. Текущий fallback жёстко указывает на `page_2`; его `safeSelect()` отключает listener, поэтому изменение selected item само по себе не гарантирует замену отображаемого Fragment.

## Goals / Non-Goals

**Goals:**

- Иметь один результат классификации выбранного BLE-устройства, доступный потокам подключения Android и iOS.
- Дать INDY3 самостоятельные явные функции генерации виджетов и init-запросов.
- Заменять опубликованный набор виджетов целиком при выборе профиля устройства.
- Применять widget-driven visibility ко всем пунктам Android bottom navigation и iOS tab bar и согласованно переключать выбранный экран.
- Сохранить дополнительное ограничение доступа для служебной вкладки.
- Активировать INDY3-профиль в iOS-потоке подключения.

**Non-Goals:**

- Не вводить в этом change отдельные классы `WidgetGenerator` для каждой модели; они появятся при добавлении следующих профилей устройств.
- Не объединять декларации стандартных V3- и INDY3-виджетов в общий builder/profile.
- Не менять протокол, виджеты и init-последовательность стандартных V3-устройств.


## Decisions

### 1. Общая классификация возвращает профиль устройства

В commonMain ввести типизированный V3-профиль (например, `INDY3`, `STANDARD_V3`, `NOT_V3`) и единый классификатор серийного номера. Наиболее специфичное правило `INDY3` выполняется до стандартных V3-маркеров и общих Android IND/INDY-правил.

На Android `checkOurLEName()` остаётся точкой фильтрации списка и делегирует классификатору проверку известного профиля; `getProtocolType()`, `StartActivity` и BLE-инициализация используют тот же результат вместо повторных `contains`-проверок. На iOS `UiInterfaceModeBridgeV3` использует общий классификатор при выборе устройства. Выбранный профиль сохраняется в общем connection/UI state и доступен обоим platform BLE managers.

Редакторы имени Android и iOS используют общий профиль устройства: для INDY3 они скрывают `INDY3-` в поле и восстанавливают тот же префикс при отправке, вместо безусловной подстановки стандартного `FTHS3-`. Позиция Android-курсора вычисляется после `setText()` по фактической длине `Editable`, поскольку byte-limit watcher может синхронно обрезать значение.

Форматирование имени не применяется к виджету серийного номера: его prefill использует исходную строку из `ParameterStoreV3`/connection state, включая семейный префикс.

Альтернатива — установить глобальный профиль как побочный эффект булевого Android `checkOurLEName()`. Она отклонена: метод вызывается для каждого элемента сканирования и недоступен iOS, поэтому значение могло бы относиться к последнему обработанному устройству, а не к выбранному пользователем.

### 2. INDY3 получает самостоятельную функцию генерации виджетов

Добавить `generatedHardcodeWidgetsINDY3()` в общий V3-парсер. Функция самостоятельно объявляет полный INDY3-набор из 16 виджетов и не вызывает стандартную `generatedHardcodeWidgets()` для последующей фильтрации. Android и iOS выбирают одну из этих функций по активному общему профилю. Это делает возможности устройства явными и соответствует будущему переходу к отдельным классам генераторов.

Функция может переиспользовать только общую техническую публикацию: очистку предыдущего опубликованного набора, назначение `widgetId/widgetPosition`, генерацию parameter structures, преобразование в UI-модели и emission обновления. Общая публикация не является общим builder списка.

До публикации необходимо заменить, а не дополнить `UiState.listWidgets`, чтобы отсутствующие у INDY3 элементы другого профиля не сохранялись между подключениями или повторной инициализацией.

Альтернатива — построить стандартный V3-набор и удалить четыре виджета и `display = 0`. Она отклонена, поскольку не даёт INDY3 собственного явно контролируемого контракта и усложняет будущие независимые генераторы.

### 3. Каждая платформа получает самостоятельную INDY3 init-последовательность

Добавить `buildINDY3InitRequests()` с десятью явными request/expected-response парами в Android `BLEController` и iOS actual `BleManagerKmm`, поскольку platform request wrappers имеют разные типы. Выбор между ней и `buildV3InitRequests()` выполняется по активному общему профилю до запуска platform progress tracking. Таким образом progress total и completion соответствуют фактически отправленному списку на обеих платформах.

INDY3-список не строится фильтрацией результата стандартной функции: отдельный список снижает риск случайной отправки новой стандартной команды неподдерживающему устройству после будущего расширения V3.

### 4. Платформенная навигация использует таблицу item → display

Android `BottomNavigationController` и iOS `MainTabBarController` используют одинаковую логическую таблицу соответствий:

| Menu item | Display |
|---|---:|
| `page_1` (жесты) | 0 |
| `page_2` (сенсоры) | 1 |
| `page_4` (специальные настройки) | 2 |
| `page_3` (обучение) | 3 |
| `page_secret` (служебные настройки) | 4 |

На Android `applyVisibility(visibleDisplays)` обходит всю таблицу. На iOS контроллер пересобирает/фильтрует доступные view controllers по той же таблице, сохраняя устойчивый tag каждой вкладки. Обычный item видим тогда и только тогда, когда его `display` присутствует в `visibleDisplays`. Для служебного item итоговая видимость равна `displayAvailable && secretAccessEnabled`; сохранённый access-флаг не должен напрямую делать пустой экран видимым.

Android `computeVisibleDisplays()` и iOS `DataFactory.prepareData(display:)` остаются источниками фактического наличия виджетов. Пересчёт на обеих платформах вызывается после публикации, замены и очистки списка через существующие update-события/bridges.

Альтернатива — добавить отдельные `if` для каждого `page_*`. Она отклонена как плохо расширяемая и допускающая расхождение display mapping.

### 5. Platform fallback выбирает только доступный экран и синхронно открывает его

После применения видимости Android/iOS controller проверяет текущий item. Если он скрыт, fallback выбирается в следующем порядке:

1. `page_2`, если экран сенсоров доступен;
2. первый видимый item в порядке меню;
3. отсутствие selection, если видимых items нет.

На Android выбор fallback должен одновременно обновить selected item и открыть соответствующий Fragment через единый routing method; нельзя ограничиваться текущим `safeSelect()`, отключающим listener. На iOS необходимо согласованно обновить `selectedViewController` после фильтрации `viewControllers`. При отсутствии доступных items контейнер bottom navigation/tab bar скрывается; при появлении первого доступного item он снова показывается с учётом существующих platform loader/IME/chrome-ограничений.

Существующий `pendingReturnItemId` можно сохранить: автоматическое возвращение допустимо только пока пользователь не выбрал другой item вручную и только если исходный item снова стал видимым.

## Risks / Trade-offs

- [Дублирование деклараций между стандартным V3 и INDY3] → Принято как осознанная временная плата за явные независимые профили; при появлении новых устройств перейти к `WidgetGenerator`-классам отдельным change.
- [Смешение widget availability и секретного доступа] → Хранить access-флаг отдельно и вычислять итоговую видимость как конъюнкцию двух условий.
- [Навигация может пересчитаться до загрузки виджетов и временно скрыть все items] → Скрывать контейнер при пустом наборе и повторно применять visibility после публикации виджетов.
- [Визуально выбранный fallback может не совпасть с Fragment] → Использовать единый route/select operation, который выполняет обе операции атомарно.
- [Более общее IND-правило снова перехватит будущий профиль] → Упорядочить классификационные правила от специфичных к общим и покрыть конфликтующие префиксы unit-тестами.
- [Пересборка iOS `viewControllers` может нарушить custom tab overlay или выбранный tag] → Фильтровать стабильный каталог tab descriptors, затем обновлять overlay и selection по tag, а не по старому индексу.

## Migration Plan

1. Добавить общую V3-классификацию и перевести Android/iOS selection flows без изменения поведения известных моделей.
2. Добавить общий INDY3 widget generator и platform INDY3 init-функции с ветвлением по активному профилю.
3. Обобщить Android bottom navigation и iOS tab bar mapping/fallback.
4. Запустить shared, Android и iOS unit/UI/regression tests для стандартного V3 и INDY3.
5. При необходимости rollback вернуть выбор стандартных V3-функций и старые platform visibility implementations; формат сохранённых пользовательских данных не изменяется.
