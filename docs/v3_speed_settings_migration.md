## Область

Выбран `P_KEY_SPEED_SETTINGS`: один числовой слайдер «Настройка скорости»
в `AdvancedFragment` (`display = 2`). Он задаётся приложением как для
стандартного V3, так и для INDY3. В отличие от усиления пары EMG-каналов и
toggle-slider, этот сценарий работает с одним целым значением.

Существующие имена участка: `SliderDelegateAdapterV3` → `SliderItemV3` →
`SliderParameterWidgetSStruct`, ключ параметра — `P_KEY_SPEED_SETTINGS`.
В плане и новом коде сохраняем терминологию Slider; скорость обозначает
конкретный параметр этого виджета, а не новый тип виджета.

Динамическая UBI4, остальные V3-параметры, XML и генерация виджетов внутри
`BLEParserV3` сохраняются. Извлечение касается только Android-логики вокруг
параметра скорости, а не всего `SliderDelegateAdapterV3` за один шаг.

## Чтение и обновление

1. `BLEController.initRequestsV3()` выбирает список запросов по профилю.
   И `buildV3InitRequests()`, и `buildINDY3InitRequests()` включают GET скорости.
2. `BLECommandsV3.request(0x3E)` формирует пакет `00 0F 3E 00 CRC`.
   Используется существующее вычисление CRC, без новой реализации.
3. Входящие данные поступают через `BLEController.parseReceivedDataV3()` в
   `BLEParserV3.parseReceivedData()`.
4. `WidgetResponseRoutesV3` сопоставляет ответ `0x0F/0x3E` с `P_KEY_SPEED_SETTINGS`
   и `SLIDER_FLOW`.
5. `ParameterCodecRegistryV3.decodeFromPayload(SLIDER, ...)` читает `payload.u8(1)`
   и создаёт `ParameterTypedValueV3.Slider`.
6. `BLEParserV3.handleWidgetRoute()` записывает значение в `ParameterStoreV3`,
   сериализует его в `ParameterProvider`, публикует соответствующее событие.
7. Android-слайдер фактически подписан на `ParameterStoreV3.updates` и фильтрует
   обновления по ключу. При первоначальном показе он читает текущее значение;
   если его нет в store, пробует декодировать строку из `ParameterProvider`.

`DataFactory.prepareData(2)` готовит элементы списка, а `AdvancedFragment`
передаёт их существующему составному адаптеру. Генерация структуры и живые
значения параметра — разные источники; при миграции это различие сохраняется.

## Действия пользователя и запись

- При перетаскивании SeekBar меняется подпись; SET отправляется после отпускания.
- Кнопки `+`/`−` меняют значение на 1 с ограничением по диапазону. Отправка
  откладывается на 300 мс после последнего нажатия для этого виджета.
- Доступность ввода определяется `UiState.v3WidgetsInteractionEnabled`.
- При уничтожении представления адаптер отменяет таймеры и подписки.

Текущий `SliderDelegateAdapterV3.sendProgress()` для скорости выполняет:

1. Поиск метаданных и кодирование `SetInt` через существующий codec.
2. Создание SET-пакета `00 0F 3D VALUE CRC` через `BLECommandsV3.sendCommand()`.
3. Оптимистическую запись нового значения в `ParameterStoreV3`.
4. Вызов `SettingsProfileManager.saveBleValue()` — сохранение запускается асинхронно.
5. Сериализацию значения в `ParameterProvider`.
6. Постановку пакета в текущую очередь через `MainActivityUBI4.bleCommandWithQueue()`,
   характеристика `SERIALPORTCHAR_UUID`, тип `WRITE`.

Профиль сохраняется существующим `SettingsProfileRepository` через Room DAO
с привязкой к серийному номеру и активному профилю. Если текущий serial пустой,
manager пропускает сохранение. Завершение записи в БД не ожидается перед BLE SET.

## Что сейчас означает подтверждение

- `ParameterStoreV3` обновляется и локально при SET, и парсером при ответе.
  Само изменение этого store не доказывает ответ устройства.
- В `sendProgress()` нет отдельного GET скорости после каждого SET и нет
  ожидания совпадающего значения readback; callback очереди передаётся пустым.
- Callback отправки/GATT и завершение очереди не равны подтверждению применения
  значения. В частности, `writeData()` может завершиться и при отказе dispatch.
- Входящий ответ обновляет отображаемое значение по существующему пути.
  Фактическое поведение устройства после SET в этой проверке не измерялось.

Первый рефакторинг сохраняет оптимистическое обновление и существующий порядок
операций. Он не добавляет новые GET, таймауты, повторные отправки, rollback или
надпись «подтверждено устройством». Такие изменения требуют отдельного решения.

## MVVM с потоком состояния в стиле MVI

Базовый пакет новых классов: `app/.../ubi4/versions/v3/`.
Скорость переносится как первая часть экрана дополнительных настроек V3
(`AdvancedFragment`, `display = 2`). Отдельная ViewModel на слайдер не создаётся.

- `domain/settings/V3DeviceSettingsRepository`: контракт чтения и изменения
  настроек устройства V3. Сначала содержит только нужные операции скорости,
  без Activity, BLE-пакетов, Room и типов parser/widget-структур. Связанные
  настройки добавляются по мере миграции, независимо от их UI-виджета.
- `data/settings/V3DeviceSettingsRepositoryImpl`: Android-адаптер к текущим
  store, codec, профилю и предоставленному порту отправки в существующую очередь.
- `presentation/advancedsettings/V3AdvancedSettingsViewModel`: принимает действия
  и данные репозитория для перенесённой части дополнительных настроек V3.
- `presentation/advancedsettings/V3AdvancedSettingsUiState`: неизменяемое
  состояние этой части экрана, доступное через StateFlow; сначала только скорость.
- `presentation/advancedsettings/V3AdvancedSettingsAction`: действия экрана
  для существующего типа Slider: изменение значения, завершение перетаскивания,
  нажатия `+`/`−` с идентификацией параметра. Для первого сценария используем
  существующий ключ `P_KEY_SPEED_SETTINGS`; отдельную Speed-терминологию не вводим.
- `presentation/advancedsettings/V3AdvancedSettingsViewModelFactory`: создаёт
  ViewModel через Android lifecycle. ViewModel не хранит Activity, View, binding
  или собственную копию BLE-сессии.

После проверки первого сценария переносим небольшие группы параметров с общим
поведением, расширяя соответствующие модели экрана и контракт настроек.
Отдельные репозитории и ViewModel для каждого виджета не планируются.

Контракт, data-реализация и классы presentation уже добавлены для первого Slider.
`domain/settings/usecase/SetSliderValueUseCaseV3` проверяет допустимый диапазон
и актуальную блокировку перед записью через репозиторий.

Поток записи: `UI Action → ViewModel → UseCase → domain-контракт → существующий механизм`;
данные репозитория и локальные действия формируют `UiState → render`.
Render/подписка не запускают отправку команды. Временный черновик и отображаемое
значение не подменяют сохранённые данные устройства. Подтверждённость значения
не выводится из store, который смешивает локальные и входящие обновления.

MVI задаёт порядок обработки событий. Хранилищем состояния экрана в памяти
будет StateFlow, долговременные данные продолжат храниться существующим способом.

## Критерии будущего переноса

1. Стандартный V3 и INDY3 сохраняют виджет скорости; UBI4 и другие параметры идут прежним путём.
2. Начальное и последующие значения корректно отображаются без отправки SET из render.

## Связь Fragment с ViewModel и правила domain (2026-09-09)

`BaseWidgetsFragment` создаёт ViewModel с владельцем `this`, принимает действия

repeatOnLifecycle(STARTED). Состояние содержит activeGestureId и
isInteractionEnabled, действия — ViewAttached/Detached и GestureSelected.
Fragment передаёт состояние адаптеру, адаптер отображает прежние название,
подсветку и блокировки. Его локальный кэш состояния используется для render
и пока ещё существующей загрузки группы ротации, но не выбирает активный жест.

SelectGestureUseCaseV3 проверяет ID (1–15 и 64–77), доступность управления
и устройство. Жест 12 по-прежнему скрыт в коллекции, но допустим в протоколе.
RequestActiveGestureUseCaseV3 проверяет доступность запроса и устройство.
V3GesturesRepositoryImpl использует ParameterStoreV3/ParameterProvider,
SettingsProfileManager и прежнюю очередь. Сохранён порядок: локальное значение,
профиль, сериализованный кэш, SET 15/0x25/ID. GET остаётся 15/0x24/0.
Чтение состояния и входящие данные не отправляют SET; явное повторное нажатие
на тот же жест по-прежнему отправляет одну команду на каждое нажатие.

Запрос активного жеста выполняется при входе/возобновлении управления, без
повторного запроса из onBind. При блокировке или уходе состояние отключает
управление и сохраняет прежнюю надпись «Unknow». Запоздалое действие после
очистки ViewModel, смены устройства или исчезновения параметра не отправляет SET.
Подписки Fragment начинаются в onViewCreated; отложенный render проверяет
текущую View и отменяется при её уничтожении.

Удалены persistActiveGesture/sendActiveGesture, собственная подписка адаптера
на активный жест, а также sendBLEActiveGestureV3/requestActiveGestureV3 из Base.
Состав через DataFactory, редактирование группы, фильтры и настройки жеста
пока остаются на прежнем пути. Это завершение сценария активного жеста,
а не всего экрана. Следующий шаг — C1.2, группа ротации.

Проверка: 488 app-тестов в 53 классах (25 новых), без ошибок и пропусков;
лог `/tmp/ubi4-c1-verify.log`. На Android-эмуляторе прошли 4 теста: выбор
из коллекции/кастомных жестов/группы, входящие данные, блокировка, пересоздание
View, повторный bind и возврат через нижнее меню; скрытая вкладка INDY3;
два регрессионных сценария Service. Все BLE-пакеты перехвачены debug hooks;
лог `/tmp/ubi4-c1-instrumentation-final.log`. Обычные debug/release APK
успешно собраны (`/tmp/ubi4-c1-final-build.log`). Реальное устройство не
использовалось. Shared, парсеры/генераторы, iOS, XML/Compose, Gradle-модули
и папки других авторов не изменялись.

## Падение 3D-превью при переходах (2026-09-16)

Лог Samsung SM-A065F за 15 сентября, 19:35:35: SIGBUS в
`libGLES_mali.so → eglDestroyContext`, вызванный очисткой
`CollectionGestureCardGLSurfaceViewV3`. При уходе с экрана очистка одной
поверхности ставилась в очередь дважды: из `onDetachedFromWindow` и
`onSurfaceTextureDestroyed`. Остановка GL-потока также могла пересечься
с повторным присоединением той же View.

Освобождение поверхности оставлено в `onSurfaceTextureDestroyed`.
Создание, отрисовка и удаление EGL-контекстов используют общий существующий
замок коллекции; карточка освобождает собственные контекст и поверхность,
не завершает общий EGL display. Состояние драйвера для потока очищается
через `eglReleaseThread` до его остановки. Завершение старой задачи очистки
проверяет поток и поколение поверхности, чтобы не остановить новую сессию.
Внешний вид, BLE, shared и другие ветки приложения этим исправлением не менялись.

Добавлен `V3GesturePreviewLifecycleTest`: 12 циклов переходов между «Жестами»,
«Сенсорами» и «Спецнастройками», запуск анимации и повторное присоединение
TextureView с ожиданием настоящего первого кадра. BLE перехватывается debug hooks.
На прежнем коде в отдельном пакете на Samsung воспроизведено падение при очистке
GL-потока (`libGLES_meow.so`, SIGSEGV). Это другой стек внутри того же пути
очистки, а не точное повторение исходного SIGBUS.

Дополнительно перед удалением контекста ожидается завершение GPU-команд
карточки; общий кэш публикует ресурсы только после завершения их загрузки.
SurfaceTexture освобождается на UI-потоке после окончания EGL-очистки и
возврата Android из callback уничтожения поверхности. Ожидание GPU в каждый
кадр не добавлено. Тест навигации использует обработчик пункта меню, чтобы
анимация панели не мешала клику.

Промежуточный вариант ещё воспроизводил SIGBUS в Mali. После добавления
ожидания GPU отдельный прогон на Samsung прошёл: 12 циклов переходов и
четыре повторных присоединения TextureView (`/tmp/ubi4-gl-gpu-finish-phone.log`).
Последующая объединённая проверка выявила другое падение — RenderThread /
libhwui при удалении RenderNode; после неё освобождение SurfaceTexture
перенесено на UI-поток. Полный аппаратный автопрогон этой последней правки
не повторялся: пользователь запретил EMU на телефоне. Эмулятор проверяет
логику экрана, но не подтверждает работу Mali из-за ошибки компиляции шейдера.

Итоговая сборка установлена с сохранением данных в используемую пользователем
копию `com.bailout.stickk.gesturecrashtest`. При обычном запуске с реальным
**00001** проверены «Датчики» → «Жесты», группа ротации, возврат в коллекцию,
«Спецнастройки» → «Жесты» → «Датчики». Превью и список группы отображаются,
подключение сохранено, процесс 5808 не перезапускался; в crash-буфере новых
падений после 14:30 нет. Это ограниченная проверка переходов, а не доказательство
отсутствия всех аппаратных сбоев. Параметры, выбор жеста и калибровка не менялись.
Логи: `/tmp/ubi4-00001-navigation.log`, `/tmp/ubi4-00001-final-crash.log`.
В дальнейшем на физическом телефоне использовать только 00001; EMU оставлен
для Android-эмулятора. При последующей оценке скорости учитывать наблюдавшееся
ожидание общего GL-замка при одновременной инициализации карточек до 2,6 с.

## C1.2.1 — загрузка и отображение группы ротации (2026-09-16)

Список группы входит в `V3GesturesUiState.rotationGroupGestureIds` той же
экранной ViewModel. Fragment передаёт состояние адаптеру. Порядок и дубликаты
с устройства сохраняются, нулевые позиции исключаются; прежние пустой список,
пояснение и кнопка добавления отображаются без нового UI.

`LoadRotationGroupUseCaseV3` запускает GET через `V3GesturesRepository`,
ожидает ответ и сохраняет прежние пять повторов с интервалом 400 мс.
Подписка устанавливается до запроса и принимает даже ответ, совпадающий
с кэшем. Уход с экрана/раздела, блокировка, очистка ViewModel и смена устройства
отменяют ожидание. Явное нажатие раздела повторяет загрузку; обычный rebind
или обновление состояния повторных запросов не создаёт. Исправлен обнаруженный
UI-тестом двойной GET при первом открытии раздела.

Чтение ParameterStore и цикл повторов удалены из адаптера, старый callback
GET — из BaseWidgetsFragment. Реализация репозитория читает типизированное
значение с прежним fallback и отправляет исходный пакет 0x35. Общие парсер,
генератор, очередь, shared, UBI4, iOS и XML/Compose не менялись.

Редактирование группы пока использует прежние диалоги и сохранение, поэтому
`WidgetState.rotationGroupGestures` временно обновляется при отображении.
Удалить этот мост вместе со старым добавлением/удалением/перестановкой нужно
в C1.2.2; весь экран ещё не объявляется завершённым.

INDY3 и регрессия калибровки обоих вариантов. Проверены ответ без изменения
значения, порядок/дубликаты, пустая группа, повторная привязка списка и отсутствие
SET при отображении. На реальном 00001 открыта группа из пяти жестов;
