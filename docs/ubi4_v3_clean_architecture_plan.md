## Уточнение расположения UI — 2026-09-22

BLEController исключён пользователем из дальнейших изменений. Это ограничение
имеет приоритет над старыми этапами ниже; существующие вызовы контроллера сохраняются.

Папка `ui` и `versions/v3/presentation` сейчас обе содержат presentation-код.
Целевая организация: чисто V3-экран собран в существующем
`versions/v3/presentation/<сценарий>`: Fragment/Compose, ViewModel, UiState, Action,
его mapper/диалоги. Общий для версий экран и общая графика остаются в `ubi4/ui`.
Суффикс V3/UBI4 не определяет владельца — сначала проверяем фактические вызовы.
Domain/data/di остаются на текущих местах; имена классов при переносе не меняем.
Не создаём параллельные `ui/v3` и `presentation/v3`, копии Fragment или новые Host
ради перемещения файлов. В одном feature не нужны подпапки из одного файла.

U1 выполнен: `AccountFragmentStatisticsV3` и `V3AccountStatisticsChartMapper`
перемещены из `ui/fragments/account/statisticsFragmentV3` к существующим трём
классам `presentation/accountstatistics`. Перенесён и существующий тест mapper;
старые файлы/пустые папки удалены. UI, lifecycle, запросы и ресурсы сохранены.
Общий `GestureUsageChartView` остаётся на месте. Обновлены imports и точные пути
архитектурных тестов. Только этому Fragment разрешён импорт его ViewModelFactory;
запреты Repository/UseCase/data/BLE для UI и DI для ViewModel сохранены.
В существующий файл Fragment добавлено сопоставление прежнего полного имени
при восстановлении стека; wrapper устанавливается до super.onCreate и делегирует

Добавлен regression-тест старого/нового имени и сохранения фабрики других экранов.
Проверка U1: 847 app unit-тестов прошли без ошибок и пропусков;

Аппаратное открытие/возврат и полное восстановление Activity не проверялись.

## 1. Постоянные решения

- Сохраняем Gradle-модули `app`, `shared`, `bluetooth`, `delegateadapter`.
- BLEController не меняем, не дробим и не переносим его обязанности в рамках
  следующих шагов. Ограничение распространяется и на будущую работу после merge,
  пока пользователь явно не пересмотрит его.
- Область задачи уточнена пользователем 2026-09-16 по заданию тимлида:
  приводим в порядок только V3 (STANDARD_V3 и INDY3). Рефакторинг UBI4
  исключён из плана, в том числе после завершения V3.
- Общие Fragment, MainActivityUBI4, BaseWidgetsFragment, DataFactory, ресурсы
  и инфраструктура имеют потребителей обеих версий. Их наличие не означает,
  что весь файл относится к UBI4 или весь доступен для рефакторинга V3.
  Пользователь явно разрешил менять общие файлы при сохранении логики приложения
  и работоспособности UBI4. Выделяем V3-обязанности, сохраняем UBI4-пути и проверяем
  влияние каждой общей правки на обе версии. Это разрешение не расширяет задачу
  до архитектурного переноса UBI4.
- У V3 состав виджетов задан приложением, у UBI4 приходит от устройства/CRC-кеша.
  Эти способы формирования экрана остаются разными.
- `BLEParser` и `BLEParserV3`, включая существующую генерацию виджетов,
  остаются без переработки. Общую инфраструктуру не копируем для каждого экрана.
- Не редактируем `iosApp`, `shared/src/iosMain`,
  `old_electronic_by_Misha`, `new_electronic_by_Rodeon`.
- Сохраняем XML, Compose, OpenGL, внешний вид, порядок виджетов, локализацию,
  протоколы, очередь, ключи настроек, базу и сохранённые данные.
- Уточнение пользователя 2026-09-11: UI и способы отображения остаются прежними.
  Архитектурный перенос не добавляет блоки ошибок, индикаторы, кнопки, сообщения
  или новые повторы операций. Уже имеющиеся флаги ошибок в UiState сохраняются;
  новое отображение для них в текущий рефакторинг не входит.
- Уточнение пользователя 2026-09-16: при переносе не менять существующую логику.
  Правила, лимиты, порядок и поведение сохранения переносим как есть. Замеченные
  особенности не исправляем попутно; изменение поведения требует отдельного запроса.
- MVVM: ViewModel принадлежит конкретному экрану. MVI: действие → обработка →
  неизменяемый UiState → отображение. StateFlow не заменяет постоянное хранилище.
- Правила и сценарии — domain; BLE/БД/сеть — data; подготовка UI и его состояние —
  presentation. Зависимости: `presentation → domain ← data`.
- Конструкторы и небольшие фабрики; внедрение Hilt/Koin, новые Gradle-модули,
  обновление библиотек и универсальный MVI-фреймворк в план не входят.
- Используем существующие названия Slider, ToggleSlider, Spinner, Switch, Plot,
  Gestures и ключи параметров. Не вводим Legacy/Migrated в названия.
- Один запрос — небольшой законченный шаг текущего этапа. Размер шага можно
  увеличить по просьбе пользователя, сохраняя границы и проверки.
- Исправление `BindingGroupV3Test` отложено пользователем. Не меняем привязки
  и парсеры ради запуска этого теста; ограничение явно учитываем в результатах.

## 2. Единица работы — законченный экран

Стратегия: доводим до полной цепочки один экран, затем переходим к следующему.
Внутри экрана переносим типы виджетов по очереди, когда этого требует его состав.
Готовые обработчики переиспользуем на других экранах.

Первый экран — `SpecialSettingsFragment` (display=2).
Он содержит разделы настроек протеза и приложения. Текущий маршрут:
`page_4 → showSpecialScreen() → SpecialSettingsFragment`.
Затем `SensorsFragment` (display=1), `ServiceFragment` (display=4),
далее остальные экраны и сценарии V3 по порядку раздела 7.

Законченный экран получает из своего UiState:
- состав, порядок и устойчивые идентификаторы элементов;
- их значения и доступность;
- состояние загрузки/синхронизации и значимые ошибки, относящиеся к этому экрану.

Граница SpecialSettings уточнена при завершении A6: загрузка/операции профилей,
autoLogin и ошибки настроек принадлежат экрану. Общий SyncProgressDialog и его
синхронизация принадлежат Activity; их состояние не дублируем в экранной ViewModel
без отдельного потребителя. Готовность параметров приходит через repository.

В V3-пути Fragment отображает состояние и передаёт действия. Он не читает
`UiState.listWidgets`, не вызывает `DataFactory.prepareData()` и не собирает
BLE-пакеты. Адаптеры не обращаются к ViewModel, репозиториям или глобальным stores.
Служебные одноразовые эффекты вводим только для реальных сценариев навигации,
диалогов и сообщений; правила доставки определяем явно.

Не считаем экран завершённым только потому, что обработчики его Slider перенесены.

### Расположение общих Fragment и граница версий

SensorsFragment, SpecialSettingsFragment, ServiceFragment и SprGestureFragment
сейчас подключают обе версии и остаются в `ubi4/ui/fragments`. Их package сам
по себе не нарушает Clean Architecture: важны обязанности и зависимости.
Весь общий Fragment не переносим в `versions/v3`, не переименовываем в V3-класс
и не копируем вместе с прежней логикой UBI4.

V3 ViewModel/UiState/Action, UseCase и repositories продолжают находиться
в `versions/v3`. Общий Fragment остаётся Android-точкой подключения; правила
V3 из него уходят в соответствующие слои. Если понадобится отдельный V3 Fragment,
это самостоятельное выделение конкретного экрана с сохранением прежнего UBI4-маршрута,
а не обязательное перемещение всех общих экранов ради структуры папок.

Для уже отдельных V3-only экранов применяется уточнение U1 в начале документа:
Fragment и его UI mapper постепенно собираются рядом с ViewModel/UiState/Action.
Это не означает выделение копий из перечисленных общих Fragment.

Цель — чистые границы V3 при сохранённом UBI4-пути. Оставшаяся прежняя логика
UBI4 в общем файле не является заданием на её перенос. Изменения общей реализации,
достижимой из UBI4, не подменяем формальным добавлением префикса V3: сначала
изолируем V3-потребителя. Сохраняем общие ключи preferences, данные, XML и протоколы;
сами по себе они не должны становиться несовместимыми между версиями.

### Судьба bindV3SliderSettings и BaseWidgetsFragment

`bindV3SliderSettings` сейчас архитектурно допустим как временное соединение
слоёв: Fragment владеет ViewModel и подпиской через
`viewLifecycleOwner.repeatOnLifecycle(STARTED)`, адаптер отображает состояние.
Откатывать эту работу не нужно.

Но базовый Fragment не становится постоянным владельцем поведения всех экранов.
Фиксируем порядок его сокращения:
1. В A2 подписка и действия SpecialSettings перенесены в `SpecialSettingsFragment`.
   Его владелец — `V3SpecialSettingsViewModel`, фабрика —
   `V3SpecialSettingsViewModelFactory`, состояние — `V3SpecialSettingsUiState`.
   Пакет — `presentation.specialsettings`; имена V3AdvancedSettings из кода удалены.
2. Общая логика выделена в `presentation.sliders/V3SliderSettingsStateHolder`
   с явно переданным viewModelScope. Sensors с B1 использует собственную
   `V3SensorsViewModel`, Service с B2.1 — `V3ServiceViewModel`. Advanced пока
   использует нейтральную `V3SliderSettingsViewModel` через прежний binder.
   Остальные действия Service завершаются в B2; domain/data не копируются.
3. Пока экран не переведён, его рабочий путь через `bindV3SliderSettings`
   сохраняется. После перевода последнего потребителя этот метод и временная
   настройка `v3SliderParameterKeys` удаляются из BaseWidgetsFragment.
   Проверка B3 (2026-09-15): у AdvancedFragment нет входа из текущей навигации.
   showAdvancedScreen вызывается только запасным возвратом из справки, если её
   источником уже был AdvancedFragment; это не самостоятельный вход на экран.
   Его перенос исключён из текущего этапа. Прежнюю привязку пока сохраняем;
   удаление неиспользуемого экрана и связанных остатков рассматриваем в C4.
4. Из BaseWidgetsFragment выделяются обязанности V3 при переносе конкретных
   экранов. Общие реализации и UBI4-обязанности остаются на месте; глобальная
   очистка базового класса вне задачи. Удалять заменённый код можно только после
   проверки, что он не используется UBI4 или другими сохранёнными сценариями.

Это заранее запланированное завершение перехода, а не смена стратегии по ходу.
Новые ToggleSlider/Spinner-подписки в BaseWidgetsFragment не добавляем.
При отделении SpecialSettings сначала сохраняем работоспособность Slider на Sensors/Service;
не расширяем общую ViewModel до модели поведения всех экранов приложения.

## 4. Границы shared, DataFactory и domain

`shared` — модуль переиспользуемого кода, а не отдельный архитектурный слой.
В нём могут находиться data, domain и общая presentation-логика.

Существующая цепочка состава ещё не перенесённых экранов и UBI4:
`BLEParser/BLEParserV3 → UiState.listWidgets → DataFactory.prepareData(display)
→ List<Any> с SliderItemV3/другими Item → Fragment → адаптеры`.

После A3 состав SpecialSettings V3 проходит через
`DataFactoryV3SpecialSettingsWidgetsSource → V3SpecialSettingsWidgetMapper
→ V3SpecialSettingsViewModel → UiState.widgets → Fragment`.
Преобразователь создаёт совместимые Items для прежних адаптеров на UI-границе.
Domain не зависит от DataFactory и UI-структур.

Цепочка значений настроек:
`входящий пакет → существующий кодек/store → Repository → Observe UseCase → ViewModel → UiState`.
Действие идёт через `Fragment → ViewModel → UseCase → Repository → текущая очередь`.
Это пути данных/вызовов, а не обратные зависимости domain от реализации репозитория.

DataFactory фильтрует по display, сортирует, выбирает подписи и создаёт UI Items.
Эти обязанности относятся к подготовке представления.
Папка `shared/.../data` также содержит Room, сеть, парсеры, состояния и структуры;
массовый перенос всей папки в один слой не выполняется.

| Обязанность | Целевое место |
| --- | --- |
| Параметры устройства, ограничения и зависимости настроек, UseCase и repository-контракты | Domain соответствующей версии |
| Парсеры, кодеки, BLE-пакеты, БД, сеть, преобразование транспортных данных | Data; существующие парсеры остаются на месте |
| Состав и порядок UI, подписи, преобразование в UI Items | Presentation, общая часть может быть в shared |
| UiState, действия и черновики экрана | Presentation/ViewModel в app |
| Fragment, XML/Compose, адаптеры и анимации | Android UI в app |

Не протаскиваем `Any`, `SliderParameterWidgetSStruct`, Room Entity,
Android View/Context и байты BLE в новые domain-контракты.
Domain не занимается локализацией, сортировкой RecyclerView или выбором XML.

### Совместимость с iOS

iOS напрямую вызывает DataFactory.prepareData() и использует существующие Items
и widget-структуры. Эти публичные API сохраняем.

Сначала отделяем Android-потребление через узкую границу совместимости:
существующая подготовка списка → преобразование в типизированные UI-модели →
состояние экрана. Разбор старых `Any`/widget-структур сосредоточен в одном
presentation-преобразователе; Fragment и ViewModel не разбирают их сами.
Domain получает только понятия устройства и правила, не старые UI Items.

DataFactory остаётся источником совместимости, пока новые цепочки не покрыты
проверками. На этапе KMM выделяем только V3-код и V3-потребление. Переписывание
общей реализации DataFactory и перенаправление существующих UBI4/iOS-потребителей
на новый путь не входят в текущую задачу. Их API и поведение сохраняются.
Старые публичные модели нельзя удалить только потому, что Android ими уже не пользуется.

### Физическое размещение

На текущих Android-этапах сохраняем `app/.../versions/v3/{presentation,domain,data}`.
Пустые будущие пакеты заранее не создаём.

На отдельном этапе KMM платформенно независимые domain-модели, правила и UseCase
переезжают в `shared/commonMain/.../versions/v3/domain` с сохранением package/API.
Android ViewModel, Fragment и платформенные реализации остаются в app;
репозитории/адаптеры размещаются по их реальным платформенным зависимостям.
Это единственный запланированный перенос уже выделенного чистого domain в другой
существующий модуль; одновременно его поведение не перерабатывается.

Архитектурный перенос UBI4 исключён пользователем. Его текущие сценарии и общие
алгоритмы/инфраструктура сохраняются; новая структура относится к V3.

## 5. Правила состояния и операций

- Наблюдение, первая отрисовка и повторная подписка не отправляют команды.
- UiState содержит состояние экрана и черновики; подтверждённое устройством
  значение не приравнивается автоматически к локально выбранному.
- Сохраняем текущую оптимистичную запись. Подтверждения, retries и rollback
  не добавляем под видом рефакторинга.
- Business-правила выполняет domain. Таймеры жестов UI, отображение черновика
  и анимации остаются в presentation. UseCase соответствует содержательному
  сценарию, а не каждому callback или полю.
- Побочные действия выполняются вне `MutableStateFlow.update` и чистых reducers.
- Состояние устройства читается через repository-контракт; сборка UI относится
  к presentation. UseCase-посредник ради одного перенаправления не обязателен.
- Для экранной подписки используем lifecycle представления. При выходе из STARTED
  ожидающие записи отменяются; при возврате читается актуальное состояние.
- Fragment.hide() без смены lifecycle не равен STOP. Отдельно проверяем текущую
  навигацию; её семантику не меняем незаметно вместе с архитектурой.
- Создание конкретных зависимостей — точка сборки/фабрика; UI и ViewModel
  не вызывают `MainActivityUBI4.main` для работы с устройством.

В отчёте указываем номер этапа, что изменилось, какие прежние пути заменены,
