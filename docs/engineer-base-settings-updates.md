# Обновление базовых настроек инженером

## Изменение настроек пользователем

В режиме «Пользователь» выбранные «Базовые настройки» доступны только для чтения.
Попытка изменить параметр показывает диалог «Базовые настройки защищены».
«Без изменений» отменяет правку: параметры протеза, профили и выбор сохраняются.
Если есть свободный слот, «Создать профиль» копирует базовые настройки в первый
свободный личный профиль. Если все три слота заняты, диалог показывает текущее
название профиля №1 и предупреждает о замене его параметров; кнопка — «Заменить
профиль». Название профиля №1 сохраняется. Перед записью занятость слотов проверяется
повторно: изменившаяся ситуация не даёт права на непредусмотренную замену.
После подтверждения выбирается личный профиль и к нему применяется начатая правка.
Базовые значения не меняются. Смена устройства, остановка экрана и потеря доступа
отменяют отложенную правку. Инженер по-прежнему редактирует базовые настройки напрямую.

## Формат существующего API

Используется `GET/POST /v1/device-mobile-app/{deviceId}`. Поле `settings` по-прежнему
содержит JSON-строку. Внутри `BASE_SETTINGS` добавлены поля:

```json
{
  "profile_id": 0,
  "name": "Базовые настройки",
  "changed_by_service_engineer": true,
  "engineer_revision": 1793622051495,
  "is_active": true,
  "updated_ts_ms": 1793622051495,
  "settings": []
}
```

`engineer_revision` увеличивается при сохранении изменений инженером в базовом
профиле. Первичное создание базового профиля не считается инженерским изменением.
Профили №1–3 не получают этот признак. Сервер должен сохранять и возвращать новые
поля внутри `BASE_SETTINGS` без потери данных. Поддержка этого контрактом реального
сервера в рамках локальной реализации не проверялась.

## Отправка

При изменении базовых настроек инженером ставится отдельная задача WorkManager
с задержкой 3 секунды и требованием доступной сети. Последующие правки заменяют
ожидающую задачу. Эта задача не отменяется при возврате в приложение.
Неотправленная версия дополнительно помечается в базе. Отметка снимается только
после успешной публикации именно этой версии; смена роли не теряет ожидающую отправку.

Обе роли отправляют полный локальный пакет: `BASE_SETTINGS` и `PROFILE1`–`PROFILE3`
с параметрами и названиями. Личные профили из сетевого ответа не загружаются.

Перед обычной отправкой сначала загружаются сетевые базовые настройки, выполняется
согласование с настройками протеза и только затем формируется полный пакет.
Локальные личные профили, в том числе настроенные офлайн, имеют приоритет.
Ошибка чтения базовых не допускает отправку устаревшей локальной базы.

Исключение — неотправленные изменения базовых, сделанные инженером. Они сохраняются
и публикуются без замены сетевой версией; отметка ожидания снимается только после
успешной отправки соответствующей версии.

## Получение пользователем

Проверка выполняется при готовом подключении, возврате приложения на передний план
и переключении роли на пользователя. Офлайн доступно уведомление о версии, ранее
сохранённой в локальной базе.

До сетевой авторизации сохраняется снимок полученных BLE-настроек протеза. При первом
подключении он становится локальным базовым профилем, даже если интернет отсутствует.
На повторном подключении чтение протеза не создаёт личные профили до ответа сервера:
в протезе уже могут находиться новые значения инженера.

Из сетевого ответа читается только `BASE_SETTINGS`. При получении инженерской версии
сначала сохраняются **предыдущие локальные базовые настройки пользователя**, если
они отличаются от новых. Источником резервной копии служит профиль 0 из локальной
базы, а не текущие значения, прочитанные из уже перенастроенного протеза.

1. Использовать личный профиль с совпадающими старыми базовыми настройками.
2. Иначе занять первый свободный слот №1–3 (пустой стандартный профиль считается свободным).
3. Если все слоты заняты — заменить параметры профиля №1, сохранив его название.

После сохранения копии новые серверные значения и инженерская версия записываются
строго в «Базовые настройки». Если до обновления был выбран базовый профиль,
выбирается резервная копия старых значений; если был выбран личный профиль,
его выбор сохраняется. Получение данных само по себе не отправляет BLE-команд.
Версия становится доступной для существующего диалога «Принять / Пропустить».
Повторное получение той же базы не создаёт ещё одну резервную копию.

В роли инженера при получении базовых и при фоновой отправке пользовательская
резервная копия не создаётся. Профили с другого телефона не импортируются.
Более старая серверная инженерская версия не откатывает уже сохранённую новую.
Неотправленные инженерские правки сохраняют прежний приоритет.

Для базовых без инженерской версии сохраняется прежнее согласование с параметрами
протеза. Сравниваются общие известные BLE-параметры; недостающие значения, текущий
выполняемый жест и чтение параметров другого жеста не считаются правкой.

При восстановлении интернета открытое приложение повторяет получение базовых
настроек и ставит локальные личные профили на отправку через WorkManager. Эта
задача не отменяется при возврате в приложение. Фоновый Worker использует сохранённые
на телефоне параметры, если соответствующий протез сейчас не подключён.

Диалог использует тот же XML, что предложение новой прошивки, и ждёт закрытия
диалога прошивки. В роли инженера диалог не показывается.

- **Принять:** проверить серийный номер, роль, готовность подключения и версию;
  выбрать профиль 0, передать его значения через существующий BLE-applier,
  обновить выбор в виджете и сохранить просмотренную версию.
- **Пропустить:** сохранить просмотренную версию; не выбирать профиль и не
  отправлять значения по BLE. Новые базовые значения остаются в локальной базе.

Просмотренная версия хранится в настройках телефона отдельно для каждого серийного
номера. Повторное открытие или смена роли не показывает ту же версию заново. Новая
версия снова вызывает диалог. Другой телефон имеет собственную отметку просмотра.

Сохранение решения происходит после вызова BLE-applier; это не подтверждение
фактического readback всех параметров протезом. Если выбранный профиль уже базовый,
пропуск сохраняет текущие значения устройства, хотя сохранённый базовый профиль
уже содержит новые значения.

Существующий API записывает целый пакет без серверного compare-and-swap. Проверка
версии или атомарная серверная запись по-прежнему необходимы, чтобы исключить
конфликт двух одновременных отправок между GET и POST.

## Диагностика

- `SettingsProfileUploadWork`: постановка задачи `reason=engineer_base_changed`.
- `SettingsProfileUploadWorker`: начало, результат и повторы сетевой отправки.
- `BaseSettingsUpdate`: ошибки получения, принятие и пропуск с номером версии.
- `SettingsProfileSync`: сохранение предыдущей локальной базы в личный профиль,
  повторное использование резервной копии и отказ от устаревшей серверной версии.

Room: миграция 4 → 5 добавляет `engineer_revision INTEGER NOT NULL DEFAULT 0`
и `engineer_upload_pending INTEGER NOT NULL DEFAULT 0`.
