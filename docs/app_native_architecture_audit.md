# Аудит нативного Android-кода app — 2026-09-22

Это актуальная карта оставшейся работы, дополняющая основной план V3.
Аудит шире области реализации: просмотрены Android-участки вне
`new_electronic_by_Rodeon` и `old_electronic_by_Misha`, но рефакторинг поведения
UBI4 по-прежнему не разрешён. Общие файлы можно менять с сохранением всех версий.
AdvancedFragment исключён; DFU отложен до merge реализации коллеги.
Последующее уточнение пользователя: BLEController также исключён из изменений.
Его наличие в результатах аудита не является заданием на рефакторинг контроллера.

## Объём и достоверность

Инвентаризированы 396 Kotlin/Java-файлов: 394 в main и два варианта debug/release
тестовых hooks. Проверены импорты, объявления и ссылки, точки сборки зависимостей,
маршруты Manifest/навигации и ключевые реализации с BLE/preferences/глобальными stores.
Это статический архитектурный аудит, не построчное доказательство корректности
каждого метода и не аппаратная приёмка. XML/Manifest/AIDL/Gradle проверялись как
потребители и точки входа; полный аудит неиспользуемых ресурсов ещё предстоит.
Папки исключённых реализаций не рефакторились; поиск ссылок на кандидатов учитывал
их потребителей, чтобы случайно не удалить общий контракт.

## Что уже стало лучше

- В основных V3-сценариях пользовательский ввод идёт через Action → ViewModel →
  UseCase → domain Repository → data implementation; обратно приходит UiState.
- Перенесены параметры «Спецнастроек», график/пороги/кнопки «Датчиков», служебные
  параметры, роль/PIN, имя/serial, калибровка, активный жест и группа ротации.
- Отдельно перенесены статистика, серверный профиль, поддержка, информация о
  протезе, игры и V3-данные редактора жестов. Это сценарии, а не обещание чистоты
  всех строк файлов, в которых они отображаются.
- Адаптеры основных экранов создают сами экраны; DI вынесена из Fragment.
  StateHolder больше не является вторым владельцем репозитория и UseCase.
- Main получил состояние навигации/заряда/identity; синхронизация имеет свою
  ViewModel. Очередь и низкоуровневая запись выделены в BleCommandQueue/Writer.
- Правила телеметрии и выгрузки при уходе приложения выделены; последние операции
  с сохранённым подключением V3 проходят через Main ViewModel/UseCase/Repository.
- Есть проверки границ, повторных записей, отмены и устаревших результатов.
  Последняя локальная очистка убрала 48 строк из AccountFragmentMainV3/Base.

Итог: приложение находится в середине постепенной миграции. У новых участков уже
есть понятные границы и тестируемые правила, но рядом остаются старые пути.
Число файлов/успешных тестов не переводится в процент «чистоты архитектуры».

## Главные незакрытые границы

### 1. Применение профилей выходит обратно в UI-инфраструктуру

`V3SpecialSettingsViewModelFactory` передаёт `SettingsProfileApplierV3::apply`
в `V3SettingsProfilesRepositoryImpl`. Сам applier находится в adapters, обновляет
ParameterStore/ParameterProvider, собирает BLE-команды и вызывает
`MainActivityUBI4.main.bleCommandWithQueue` / `main.saveBoolean`.
Его также вызывают `Ubi4SettingsProfileReceiver` и старый путь Spinner.

Перенести существующий applier в data/settingsprofiles, дать ему транспорт и
настройки через DI; сохранить порядок записи кэша/очереди и все типы параметров.
Обновить всех трёх потребителей, удалить реализацию из adapters. Не создавать
ещё один applier поверх старого. Проверять также применение серверного импорта.
Текущие проверки импортов data не обнаруживают такой обход через callback DI.

### 2. Некоторые V3-адаптеры имеют два режима выполнения

`SpinnerDelegateAdapterV3` (834 строки) и `ToggleSliderDelegateAdapterV3`
(593 строки) содержат как обработку UiState/Action, так и прямые старые пути
с stores/BLE/preferences. `SwitcherDelegateAdapterV3` (322 строки) сохраняет
прямую работу с данными; он регистрируется в Base.

Сначала построить матрицу: профиль устройства × экран × parameterKey × адаптер ×
ветка bind. Одного наличия регистрации в Base недостаточно, чтобы считать
ветку реально используемой. Одного отсутствия виджета на обычном V3 недостаточно,
чтобы удалить поддержку INDY3/общего потребителя.
Для используемых V3-веток закончить Action/UiState; недостижимые ветки удалить
вместе с collectors, scope, model-кэшами и записью параметров. Совместимость
Advanced/UBI4 сохранять; не переносить её автоматически в новую копию адаптера.

### 3. Dashboard ещё выполняет операции устройства во Fragment

`DashboardSlotsFragment.requestSlots` меняет общий DashboardSlotsState,
собирает пакет, отправляет через Activity и запускает timeout.
`DashboardSlotContentFragment` дополнительно читает/пишет частями, сохраняет и
сбрасывает слоты, изменяет глобальный черновик.

Последовательно перенести: список слотов → чтение содержимого → редактирование
и отправка → сохранение/сброс. ViewModel владеет состоянием/задачами экрана;
UseCase задают сценарии; data скрывает общий state, BLE и разбиение пакетов.
Compose, ввод, подтверждения, размеры частей и порядок команд сохраняются.
После каждого шага удалять соответствующие методы Fragment, не оставляя два пути.
Доступ к shared Dashboard state пока адаптировать через data, парсер не переписывать.

### 4. Главный экран аккаунта перенесён только частично

`AccountFragmentMainV3` (564 строки): профиль идёт через ViewModel, но роль читается
из preferences, Fragment наблюдает UiState/FirmwareInfoState, хранит/строит список
плат, загружает каталог и файлы прошивки через YandexDiskFirmwareRepository.

Ближайший отдельный шаг — роль/доступность действий через существующий domain
сервисной роли и состояние аккаунта. Не дублировать правила PIN/доступа.
Список плат и firmware-кэш согласовать с новой реализацией коллеги; изменение
DFU/скачивания/диалогов прошивки остаётся после merge. AccountMainAdapterUBI4,
BootloaderAdapterUBI4 и CardAdapter имеют живых потребителей — удалять их нельзя.

### 5. Main, Base и соединение всё ещё имеют смешанные обязанности

MainActivityUBI4 — 1158 строк; BaseWidgetsFragment — 687; BLEController — 1665.
Main сохраняет публичные preferences-методы, BLE/DFU API, static main и общую
навигацию. `BleDependencies.v3CommandTransport` пока получает executor через
`MainActivityUBI4.main`; перенос фабрики в DI сам по себе это не устраняет.
Base сохраняет общий набор адаптеров, диалоги и BLE-методы старых потребителей.

Удалять методы только после переноса последнего V3-потребителя и проверки других
версий. Довести владение V3-транспортом до явно заданного connection scope,
не меняя порядок очереди/callback и не вводя второй BLE-controller.
Навигация, lifecycle, разрешения, показ диалогов и анимации могут оставаться в UI.
BLEController оставляем целиком по прямому указанию пользователя. Улучшения
его потребителей допустимы только с существующим API и прежним поведением;
потребность менять контроллер означает отложенный шаг. DFU отдельно после merge,
новое ограничение на BLEController автоматически этим merge не снимается.

`V3MainRepository` уже объединяет connection, identity, widgets, battery и upload.
Не расширять его всеми новыми обязанностями. Пересмотреть связность при следующем
переносе, переиспользовать существующие контракты. `getVisibleDisplays` с DataFactory
— UI-совместимость под именем Repository, а не предметное бизнес-правило.
Не менять generatedHardcodeWidgets ради исправления названия/расположения этой границы.

### 6. Общие входные экраны не охвачены экранной миграцией V3

`ScanActivity` (875 строк), ScanPresenter/Interactor, SplashScreen, StartActivity
и PinActivity ещё не образуют MVVM/MVI-цепочку. В UI есть preferences, автоподключение,
выбор версии/маршрута и подготовка устройства. Уже есть Dagger в старом scan-коде;
утверждение «во всём приложении нет DI» неверно.

Это общие входы V3/UBI4/исключённых реализаций. Выделять V3-правила выбора и
автоподключения малыми шагами; Android permissions, Intent и ActivityResult
остаются на платформенной стороне. Не удалять старые Presenter/Interactor, пока
через них работают остальные устройства. Не менять WDApplication/ApplicationGraph
из исключённой папки. Полная переделка общей scan-архитектуры сейчас вне объёма V3.

### 7. Дополнительные экраны и фоновые потребители

- AchievementsFragment читает AchievementsState, дату через Activity и вызывает
  BLE напрямую. Но в AccountFragmentMainV3 сейчас `showAchievementsItem = false`.
  Сначала подтвердить доступные маршруты; не включать скрытую кнопку ради миграции.
  Для доступного V3-сценария — ViewModel/UseCase/data; карточки, цвета и анимации остаются UI.
- BleLogFragment сам читает/сохраняет фильтр и наблюдает BleLogStore.
  Для V3 перенести данные/фильтр за ViewModel; позиция прокрутки остаётся UI.
- Help: преимущественно статический UI, не требует пустой ViewModel на каждую
  инструкцию. В SensorsFragmentHelpUBI4 есть preferences, в Help/AdvancedSettingsHelp
  выбор контента по версии; перенести только чтение доступности, сохраняя маршруты.
- SettingsProfileUploadWorker/Scheduler — инфраструктура Android; не делать
  ViewModel для Worker. Общие network-клиенты/repository допустимы в data.
- GameControlBridgeService — IPC/foreground service, не экран. Сохранить Binder,
  AIDL, Parcelable и частоту публикации; зависимости на глобальные сигналы
  изолировать data-источником при работе с этим участком, без экранной ViewModel.
- ControllerBleStatusConnection смешивает broadcast и анимацию: источник
  connection state можно отделить от отображения. BorderAnimator, BottomNavigation,
  chart mapping, recycler binding и GL lifecycle сами по себе не нарушения.

## Что сохраняем осознанно

`generatedHardcodeWidgets` / `generatedHardcodeWidgetsINDY3`, DataFactory и
DataFactoryV3*WidgetsSource остаются по решению пользователя. Это ограниченная
граница совместимости, не повод переносить UI Items и Android в domain.
Shared/iOS API и парсеры не меняем. Папки UBI4 не равны мёртвому коду:
там есть общие адаптеры и Fragment. Advanced, SprTraining/MotionTraining и
прочие UBI4-сценарии не входят в миграцию V3.

Сохраняем renderer/GLSurfaceView, XML/Compose, UI-model/mapper, ViewHolder и
диалоговые Host, когда они только отображают и передают события. Их не нужно
переносить в domain или дробить на UseCase. Длинный renderer не равен god object
бизнес-логики. 3D-редактор ещё требует аппаратной приёмки, несмотря на перенос
его V3-имени/позиций/задержек/записи в ViewModel.

## Правила завершения каждого следующего шага

1. Зафиксировать старый маршрут и его потребителей: V3, INDY3, UBI4, shared/iOS.
2. Перенести одну обязанность в существующие слои; новый класс нужен только при
   самостоятельной ответственности. Простые связанные операции допустимо группировать.
3. Переключить реальный UI/фоновый вход и удалить заменённые ветки/подписки/поля
   в том же шаге. Временное сохранение объяснить конкретным живым потребителем.
4. Проверить не только imports внутри versions/v3, но и реальные DI-callbacks,
   adapters, shared Fragment и входящие события. Не маскировать обход новым Host.
5. Проверить поведение: render не пишет; повторный bind не повторяет команду;
   после STOP/смены устройства не приходят устаревшие результаты; сохранены
   исходные тайминги, значения по умолчанию, лимиты и порядок BLE.
6. Отчитаться о числе добавленных/удалённых рабочих строк отдельно от тестов и
   комментариев, оставшихся исключениях и фактически выполненных проверках.

Рост domain (131 файл / 1582 строки) сам по себе не ошибка: здесь много небольших
моделей/контрактов. Но нельзя продолжать добавлять обёртки без удаления прежнего
пути. V3SpecialSettingsViewModel (633 строки) также требует проверки дублирования
UI-преобразований, чтобы сложность не переехала целиком из Fragment в ViewModel.
Сначала удаляем дубли; не вводим универсальный MVI-фреймворк или новые модули.

Приоритеты и конкретный следующий шаг — в актуальной очереди основного плана.

## Разбор расположения UI и целевая организация

В `app/.../ubi4/ui` 76 файлов: 49 в fragments, 18 в gripper, 4 в dialog,
по одному в main/bottom/widgets/gestures/dashboard. В `versions/v3/presentation`
ещё 70 файлов; Android-адаптеры находятся отдельно в `ubi4/adapters`.
Это части одного presentation-слоя, исторически разложенные по разным принципам:
тип Android-компонента (`fragments`), имя экрана (`mainFragmentV3`) и новая
группировка по сценарию (`presentation/accountprofile`). Различие пакетов не
означает отсутствия связи: Fragment создаёт экранную ViewModel и наблюдает её state.

### Один принцип размещения

Все классы одного V3-only экрана постепенно собираются в уже существующем
`versions/v3/presentation/<сценарий>`. Presentation включает UI и ViewModel;
Fragment в нём допустим. Не создаём ещё один корень `ui/v3` и не перемещаем
все 70 новых файлов обратно. Общий для версий UI остаётся в `ubi4/ui`.
Сохраняем имена классов, domain/data/di и ресурсы. Это целевое размещение,
а не утверждение, что перенос уже выполнен.

Пример первого небольшого переноса:

```text
ubi4/
  ui/
    main/MainActivityUBI4.kt                # общая Activity
    fragments/SensorsFragment.kt           # общий экран V3/UBI4
    widgets/GestureUsageChartView.kt        # общий View из XML
  versions/v3/
    presentation/accountstatistics/
      AccountFragmentStatisticsV3.kt       # перенести сюда существующий файл
      V3AccountStatisticsChartMapper.kt    # перенести сюда существующий файл
      V3AccountStatisticsViewModel.kt      # уже здесь
      V3AccountStatisticsUiState.kt        # уже здесь
      V3AccountStatisticsAction.kt         # уже здесь
    domain/accountstatistics/              # без изменений
    data/accountstatistics/                # без изменений
    di/V3AccountStatisticsViewModelFactory.kt
```

Показательные подтверждения общих потребителей: оба AccountFragmentMain вызывают
showDashboardSlotsScreen; редактор использует EXTRA_USE_V3_GESTURE_PROTOCOL;
GesturesOpticDelegateAdapter и GesturesTwoSectionDelegateAdapterV3 используют
общий CollectionGesturePreviewController/GLSurfaceView. Имя V3 не равно владению V3.

Адаптер одного экрана можно впоследствии поместить в его feature, если он действительно
используется только там. Общий Slider/Spinner/ToggleSlider не копируем в каждый
feature; текущие пакеты сохраняем до проверки потребителей и очистки R2.
UI Host/mapper не становятся domain-классами при наведении порядка.

Для общих компонентов тоже предпочитаем группировку по назначению, а не длинные
папки с типом класса в названии. Например, общие карточки аккаунта —
`ui/fragments/account/components`; общий Dashboard Fragment и его Android-preview —
один `ui/fragments/dashboard`. Это последующие небольшие перемещения после проверки
потребителей, без переноса shared Compose-кода в app. Пакеты общего Information,
Advanced и связанной графики пока сохраняются из-за описанных ограничений.
Не заводить бесконтрольный `common`: общий компонент обязан иметь конкретных
потребителей и предметное место, например account/components или widgets.

### Проверки перед перемещением

- Для начала достаточно U1 — двух файлов статистики. Старые файлы перемещаются,
  не копируются; новые архитектурные слои не добавляются. После переноса старая папка исчезает,
  если пуста. Поведенческий рефакторинг и переименование не смешиваются с этим diff.
- V3ArchitectureTest сейчас запрещает импорт DI всем файлам presentation.
  Fragment должен иметь право получить свою ViewModelFactory. Уточнить правило
  только для конкретной UI-точки сборки; ViewModel/StateHolder по-прежнему не
  зависят от DI, UI не вызывает Repository/UseCase и не читает data/BLE/preferences.
  Обновить проверку статистики на новый путь вместо удаления проверки.
- Обновлять imports, Manifest/XML/полные имена классов, тестовые пути и Java-доступ
  при каждом реальном перемещении. Проверить сохранение/восстановление Fragment
  и sourceFragmentClass, если затрагивается такой маршрут.
- Общий GestureUsageChartView используется в двух XML — он не входит в U1.
  Редактор зарегистрирован в Manifest; GL-классы имеют package-private связи.
  Это причины оставить их вне первого перемещения, а не объявлять неиспользуемыми.
- AccountFragmentProsthesisInformationUBI4 включён в ApplicationGraph исключённой
  папки. Его package нельзя менять без нарушения текущих границ или лишнего shim;
  сохраняем исходное расположение.
- На этом шаге выполнены только анализ и уточнение плана. Kotlin/Java/XML-код
  приложения не перемещался; BLEController не менялся; сборки не запускались.
